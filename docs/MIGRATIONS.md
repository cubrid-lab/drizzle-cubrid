# Schema migrations for `drizzle-cubrid/native` (experimental)

> **Preview, like the rest of `drizzle-cubrid/native`.** The API can change in
> any release before 1.0. Design and measured CUBRID behavior:
> [ADR 0009](adr/0009-cubrid-native-migrations.md). Verified on CUBRID 11.4
> only.

drizzle-cubrid applies migrations that are **CUBRID SQL files you keep in your
repository**. It does not use drizzle-kit, in any dialect: drizzle-kit has no
CUBRID support, and its MySQL mode generates MySQL DDL. drizzle-cubrid does not
rewrite SQL written for another database either; it refuses it.

## What is implemented and what is not

| | Status |
| --- | --- |
| Apply ordered `.sql` migrations: `migrate()` from `drizzle-cubrid/native/migrator` | ✅ Implemented, live-tested on CUBRID 11.4 |
| Record applied migrations with checksums; refuse edited, renamed or missing applied files | ✅ Implemented |
| One transaction per migration; a failed migration is rolled back whole | ✅ Implemented (DDL rollback measured on 11.4) |
| Concurrent `migrate()` calls apply each migration once | ✅ Implemented (lock row) |
| Dry run: check everything and list pending migrations | ✅ `dryRun: true` |
| Validate a folder without a database | ✅ `readMigrationFiles()` |
| Refuse SQL written for MySQL or generated by drizzle-kit | ✅ [Refusals](#refused-sql) |
| Generate the first migration from a native schema (`CREATE TABLE`) | ✅ `generateInitialMigration()` from `drizzle-cubrid/native` |
| Generate `ALTER` migrations by comparing a schema with the database or an earlier schema | ❌ Not implemented: write them by hand |
| Catalog introspection / reflection (`pull`), `push` | ❌ Not implemented |
| Down migrations / undoing an applied migration | ❌ Not supported: add a new migration that reverses it |
| drizzle-kit `generate`, `migrate`, `push`, `pull`, `studio` | ❌ Unsupported in every dialect |
| Stored procedures and functions in migration files | ❌ Refused: create them outside `migrate()` |
| Migrations for the 0.x `drizzle-cubrid` entry | ❌ Not provided |
| CUBRID versions other than 11.4 | ❌ Not tested |

## Quick start

```ts
// scripts/generate-initial.ts: once, for the first migration
import { writeFileSync } from 'node:fs';
import { generateInitialMigration } from 'drizzle-cubrid/native';
import * as schema from '../src/schema';

writeFileSync('migrations/0001_initial.sql', generateInitialMigration(schema));
```

```sql
-- migrations/0002_add_email.sql: written by hand
ALTER TABLE "users" ADD COLUMN "email" VARCHAR(100);
CREATE UNIQUE INDEX "ux_users_email" ON "users" ("email");
```

```ts
// at deploy time
import { createClient } from 'cubrid-client';
import { drizzle } from 'drizzle-cubrid/native';
import { migrate } from 'drizzle-cubrid/native/migrator';

const client = createClient({ host, port, database, user, password });
const db = drizzle(client);
const { applied } = await migrate(db, { migrationsFolder: './migrations' });
console.log(`applied ${applied.map((m) => m.fileName).join(', ') || 'nothing'}`);
await client.close();
```

`generateInitialMigration(schema)` takes the object you give `drizzle({ schema })`
(relations are skipped) or an array of tables. It writes `CREATE TABLE` with
columns, `AUTO_INCREMENT`, literal defaults, `NOT NULL`, primary keys and
unique constraints, in the order given. It throws for a table that is not a
`drizzle-cubrid/native` table, for `.default(sql\`…\`)`, and for two primary
keys on one table. Read the file before committing it.

## Migration files

- **Name:** `<number>_<name>.sql`, for example `0001_initial.sql`. The number
  sets the order; leading zeros are optional. The name is letters, digits,
  `_` and `-`.
- **Numbering:** 1, 2, 3, … with no gap and no duplicate.
- **Statements:** CUBRID SQL separated by `;`. A `;` inside a string literal, a
  quoted identifier (`"…"` or `[…]`) or a comment (`--`, `//`, `/* */`) does
  not end a statement. The last statement may omit its `;`.
- **Quoting:** use double quotes for identifiers, as drizzle-cubrid does.
  CUBRID stores table and column names in lower case even when quoted.
- **Other files** in the folder (a README, `.gitkeep`) and subfolders are
  ignored.
- **Line ends:** the checksum reads CRLF as LF, so a checkout's line-end
  setting does not make an applied file look edited.

## What `migrate()` does

`migrate(db, { migrationsFolder, migrationsTable?, dryRun? })` takes the
database from `drizzle-cubrid/native`'s `drizzle()` over a cubrid-client client
or pool, not a transaction.

1. Reads and checks every file: names, numbering and SQL. Any problem rejects
   the call with every problem listed, before the database is touched.
2. Creates `__drizzle_cubrid_migrations` (or `migrationsTable`) and
   `<migrationsTable>_lock` if they do not exist.
3. Compares the recorded migrations with the files. The record must be
   migrations 1 to k of the folder, with the same names and checksums.
   Otherwise it rejects with `'applied-mismatch'` and applies nothing.
4. For each pending migration, in its own `'read committed'` transaction:
   takes the lock row, reads the record again (another `migrate()` may have
   applied it meanwhile; then it is skipped), runs the statements in order,
   records the migration and commits.

It resolves to `{ applied, pending }`: the migrations this call applied, and
an empty `pending`. With nothing pending it runs no migration statement.
With `dryRun: true` it does steps 1 and 3 (with no record table, nothing is
applied yet), creates nothing, and resolves to `{ applied: [], pending }`.

The record table has `id`, `name`, `checksum` (SHA-256 hex) and `applied_at`
(UTC `DATETIME`). Do not edit it by hand.

`readMigrationFiles(folder)` does step 1 alone and resolves to the files with
their `id`, `name`, `fileName`, `checksum` and `statements`. Use it in CI to
check a migrations folder without a database.

## Failure and recovery

On CUBRID 11.4, DDL in a transaction rolls back with it. That was measured for
`CREATE TABLE`, `ALTER TABLE … ADD COLUMN`/`DROP COLUMN`, `CREATE [UNIQUE]
INDEX`, `DROP INDEX`, `ADD CONSTRAINT … UNIQUE`, `CREATE VIEW`, `CREATE
SERIAL`, `DROP TABLE` and `RENAME TABLE`, together with DML in the same
transaction ([ADR 0009](adr/0009-cubrid-native-migrations.md)). So:

- **A failed statement rolls its whole migration back.** None of its
  statements stay and it is not recorded; migrations before it stay applied.
  `migrate()` rejects with a `CubridMigrationError` with `code:
  'statement-failed'`, `migration` (`id`, `name`), `statement` (1-based
  `index`, `line`, `sql`) and cubrid-client's error as `cause`. Fix the file
  and run `migrate()` again.
- **A failed `COMMIT`** rejects with cubrid-client's error, whose outcome can
  be unknown (`outcomeUnknown`). The statements and the record commit
  together, so the next `migrate()` sees the migration either applied and
  recorded, or neither.
- **Never edit an applied migration.** Its checksum no longer matches and
  every later `migrate()` refuses to run. Undo the edit, or add a new
  migration.
- **Statements that were not measured** (`TRUNCATE`, `GRANT`, `CREATE USER`,
  partitioning, …) may not roll back. Put them in a migration of their own
  and check the database after a failure.
- **Back up before migrating production data.** A migration's DDL locks its
  tables until it commits: application queries on a table it altered wait
  until then (measured on 11.4), and a concurrent `migrate()` waits on the
  lock row, both as long as CUBRID's `lock_timeout` allows. Keep migrations
  short.

## Refused SQL

`migrate()` and `readMigrationFiles()` refuse these, with file, line and column,
before applying anything. Nothing is rewritten.

| Found | Why |
| --- | --- |
| `` `name` `` (backticks) | MySQL quoting, the mark of SQL generated for MySQL. Use `"name"`. |
| `--> statement-breakpoint`, a `meta/_journal.json` folder | drizzle-kit output, generated for another database |
| `ENGINE=`, `UNSIGNED`, `ZEROFILL`, `DEFAULT CHARSET`, `DEFAULT CHARACTER SET` | MySQL options CUBRID does not have. CUBRID sets a table's character set with `CHARSET <name>` and `COLLATE <name>`. |
| `/*! … */` | MySQL conditional comment: MySQL runs its content, CUBRID ignores it |
| `#` comments | MySQL syntax; CUBRID uses `--`, `//` and `/* */` |
| `USE`, `DELIMITER`, `LOCK`, `UNLOCK` | MySQL statements or client commands |
| `BEGIN`, `START`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `SET TRANSACTION` | The migrator owns the transaction |
| `CREATE [OR REPLACE] PROCEDURE` / `FUNCTION` | A PL/CSQL body contains `;`, which the splitter cannot tell from a statement end |
| `?` | Migrations take no bound values |
| Unterminated quote or comment, an empty migration, `*.down.sql`, a name that is not `<number>_<name>.sql`, gaps and duplicates | Not a valid migration folder |

CUBRID forms that resemble MySQL ones, such as `AUTO_INCREMENT = 100` as a
table option, `AUTO_INCREMENT(1, 1)`, `CHARSET utf8`, `CHANGE COLUMN` and
`RENAME TABLE`, are accepted. The validator is not a CUBRID parser: a
statement it accepts can still fail on the server, and that failure rolls the
migration back.

## Errors

Every refusal is a `CubridMigrationError` (exported from
`drizzle-cubrid/native/migrator`) with a `code` and `issues` (each with
`file`, `line`, `column`, `message`, all listed in the error message too):

| `code` | When |
| --- | --- |
| `'invalid-config'` | Bad options, or a transaction or something other than the native database given as `db` |
| `'invalid-folder'` | The folder cannot be read, holds a file that is not a migration, or is a drizzle-kit folder |
| `'invalid-sequence'` | Numbers that do not go 1, 2, 3, … |
| `'invalid-sql'` | Refused SQL or an empty migration |
| `'applied-mismatch'` | The record table does not match the files |
| `'statement-failed'` | A statement failed; the migration was rolled back |
