# Product Requirements Document — drizzle-cubrid

> **Implementation note (2026-11-12):** v0.2.1 uses legacy MySQL-derived Drizzle classes and does **not** have a verified CUBRID-native dialect or migration path. The target design exclusively uses native CUBRID SQL and database-neutral verified Drizzle primitives; other database dialects, migration tools, compatibility modes, and SQL rewriting are prohibited. See [#155](https://github.com/cubrid-lab/drizzle-cubrid/issues/155) and [#192](https://github.com/cubrid-lab/drizzle-cubrid/issues/192). This file's historical architecture diagram describes the legacy implementation and is not an approved design for the native adapter.


## Overview

**drizzle-cubrid** is an independently maintained, third-party Drizzle ORM
adapter for the CUBRID relational database. It is not an official
`drizzle-orm` dialect and has no Drizzle Kit integration.

- **Package**: `drizzle-cubrid`
- **Language**: TypeScript (strict mode)
- **License**: MIT
- **Version**: 0.2.1 (latest published)
- **Organization**: cubrid-lab

## Problem Statement

CUBRID is a relational database used in Korean government and enterprise
systems. Drizzle ORM ships MySQL, PostgreSQL and SQLite dialects but none for
CUBRID, so CUBRID users fall back to raw SQL or other ORMs.

## Current shipped behavior (0.2.x, MySQL-derived)

This section describes `main`. The published 0.2.1 predates the fixes listed
under *Unreleased* in the [CHANGELOG](../CHANGELOG.md); for example, its
`db.transaction()` still ran `BEGIN`/`COMMIT` on the shared client (#185).

### How it works

1. `drizzle(client, config?)` or `drizzle({ client, ...config })` builds a
   `CubridDatabase`. `client` is a `CubridClient`, a `CubridPool` or any object
   that implements `CubridQueryable`. Options: `logger`, `casing`, `schema` +
   `mode` (for `db.query`), and `binding` (`'prepared'` by default, or
   `'literal'`).
2. `CubridDatabase` extends Drizzle's `MySqlDatabase`, and `cubridTable` is
   `mysqlTable`. SQL is generated by a subclass of Drizzle's `MySqlDialect`
   that refuses constructs CUBRID 11.4 rejects ([#189](https://github.com/cubrid-lab/drizzle-cubrid/issues/189)).
   Generating MySQL-shaped SQL does **not** prove CUBRID compatibility.
3. `CubridSession` / `CubridPreparedQuery` extend Drizzle's MySQL session
   classes. Values are sent as typed binds through cubrid-client's
   `queryPrepared()` / `executePrepared()`; selects read array rows
   (`rowMode: 'array'`).
4. `db.transaction()` calls the client's `transaction(callback, options)`, so
   the transaction runs on a connection the driver owns for its whole
   duration ([#185](https://github.com/cubrid-lab/drizzle-cubrid/issues/185)).
   A custom client without `transaction()` falls back to `BEGIN`/`COMMIT` on
   its single connection. Nested `tx.transaction()` uses `SAVEPOINT spN` and
   `ROLLBACK TO SAVEPOINT spN`; there is no `RELEASE SAVEPOINT`.
5. Column builders are drizzle-orm's MySQL builders re-exported, plus
   `cubridSet` / `cubridMultiset` / `cubridSequence` (also exported as `set` /
   `multiset` / `sequence`), `monetary`, and date/time builders adapted to
   cubrid-client's `Date` values. No DDL is generated.

### Supported, with limits

| Area | Status | Details |
| --- | --- | --- |
| `select`, `insert`, `update`, `delete`, joins, subqueries, `$count()` | Shipped | [QUERIES.md](QUERIES.md) |
| `affectedRows`, `lastInsertId`, one-row `$returningId()` | Shipped | [#182](https://github.com/cubrid-lab/drizzle-cubrid/issues/182) |
| `onDuplicateKeyUpdate()` | Shipped | `values(col)` is rejected by CUBRID |
| Transactions, savepoints, `isolationLevel` | Shipped | 3 levels; `accessMode` and `withConsistentSnapshot` refused |
| SET / MULTISET / SEQUENCE columns | Shipped | [SCHEMA.md](SCHEMA.md#cubrid-specific-types) |
| Date and time columns | Shipped | needs a UTC client (`timezone: 'utc'`) |
| `db.query.*.findMany()` / `findFirst()` without `with` | Shipped | |
| `monetary()` | Shipped | strings; double precision ([#217](https://github.com/cubrid-lab/drizzle-cubrid/issues/217)) |
| `binary()` / `varbinary()` | Defect, do not use | [#216](https://github.com/cubrid-lab/drizzle-cubrid/issues/216) |
| Relational `with` | Refused | [#200](https://github.com/cubrid-lab/drizzle-cubrid/issues/200) |
| `.iterator()` (streaming) | Throws | not implemented |
| JSON columns, BLOB/CLOB columns | No builder | `customType` only; unverified |
| Schema migrations, DDL generation | Not provided | [#163](https://github.com/cubrid-lab/drizzle-cubrid/issues/163) |

### Verification

- Offline unit tests with a 95% coverage gate (`npm test`). They mock parts of
  `drizzle-orm` and `cubrid-client` and are not database evidence.
- A live suite, `tests/integration.test.ts` (`npm run integration`), runs in CI
  against CUBRID 11.4 only. It covers transactions, joins, write metadata,
  relational queries without `with`, collections, both binding modes, date and
  time columns, and the replacements for refused SQL. Other server versions
  are unverified ([#164](https://github.com/cubrid-lab/drizzle-cubrid/issues/164)).
- Peer ranges and what was measured: [COMPATIBILITY.md](COMPATIBILITY.md).

### Usage example

```typescript
import { createClient } from 'cubrid-client';
import { cubridTable, drizzle, eq, int, varchar } from 'drizzle-cubrid';

const users = cubridTable('users', {
  id: int('id').autoincrement().primaryKey(),
  name: varchar('name', { length: 100 }).notNull(),
  email: varchar('email', { length: 255 }).notNull().unique(),
});

const client = createClient({
  host: 'localhost',
  port: 33000,
  database: 'testdb',
  user: 'dba',
  timezone: 'utc', // needed only to read date and time columns
});
const db = drizzle(client);

const allUsers = await db.select().from(users);
await db.insert(users).values({ name: 'John', email: 'john@example.com' });
await db.update(users).set({ name: 'Jane' }).where(eq(users.id, 1));
await db.delete(users).where(eq(users.id, 1));

await db.transaction(async (tx) => {
  await tx.insert(users).values({ name: 'Alice', email: 'alice@example.com' });
  await tx.insert(users).values({ name: 'Bob', email: 'bob@example.com' });
});

await client.close();
```

```typescript
import { cubridTable, decimal, int, monetary, multiset, sequence, set, varchar } from 'drizzle-cubrid';

const products = cubridTable('products', {
  id: int('id').autoincrement().primaryKey(),
  tags: set('tags', { element: varchar('tag', { length: 50 }) }),
  categories: multiset('categories', { element: varchar('category', { length: 100 }) }),
  priceHistory: sequence('price_history', { element: decimal('price', { precision: 10, scale: 2 }) }),
  price: monetary('price'),
});
```

## Planned native architecture (not implemented)

The target design replaces the MySQL-derived classes with a CUBRID-native
dialect ([#155](https://github.com/cubrid-lab/drizzle-cubrid/issues/155),
draft architecture ADR in PR [#166](https://github.com/cubrid-lab/drizzle-cubrid/pull/166)).
None of the following exists today:

| Item | Issue |
| --- | --- |
| Independent Drizzle extension boundaries | [#156](https://github.com/cubrid-lab/drizzle-cubrid/issues/156) |
| Native table and column builders, including a decision on the collection builder names | [#157](https://github.com/cubrid-lab/drizzle-cubrid/issues/157) |
| Native SELECT and relational query generation (relational `with`) | [#158](https://github.com/cubrid-lab/drizzle-cubrid/issues/158) |
| Native INSERT/UPDATE/DELETE and generated keys; upsert/`MERGE INTO` only where verified on CUBRID | [#159](https://github.com/cubrid-lab/drizzle-cubrid/issues/159) |
| Driver and row mapping rebuilt around cubrid-client | [#160](https://github.com/cubrid-lab/drizzle-cubrid/issues/160) |
| Native transactions and savepoints | [#161](https://github.com/cubrid-lab/drizzle-cubrid/issues/161) |
| Native collection and scalar type codecs | [#162](https://github.com/cubrid-lab/drizzle-cubrid/issues/162) |
| CUBRID-native schema migrations (no Drizzle Kit MySQL mode) | [#163](https://github.com/cubrid-lab/drizzle-cubrid/issues/163) |
| Prepared-query reuse and streaming | [#165](https://github.com/cubrid-lab/drizzle-cubrid/issues/165) |
| Real-server verification beyond CUBRID 11.4 | [#164](https://github.com/cubrid-lab/drizzle-cubrid/issues/164) |
| CUBRID-only dialect boundary enforcement | [#192](https://github.com/cubrid-lab/drizzle-cubrid/issues/192) |

Goals for that design: full Drizzle integration (schema, queries, relations)
on CUBRID SQL only, CUBRID-specific DML such as `MERGE INTO` where verified, migrations
verified on a real server, and live tests for every supported server version.

## Non-Goals

- Connection pooling (provided by `cubrid-client`'s `createPool()`)
- ORM-level caching
- Drivers other than `cubrid-client`
- Prisma or TypeORM integration

## Quality Requirements

- Test coverage ≥ 95% (CI-enforced)
- TypeScript strict mode
- Biome lint with no warnings
- ESM + CJS dual output via tsup
- CI: lint, type check, unit tests, lowest supported `drizzle-orm`, Node 18
  packed-package consumer, live CUBRID 11.4 suite ([CI_VALIDATION.md](CI_VALIDATION.md))

## Example-first Design Philosophy

### Why Example-first

CUBRID's ecosystem is small compared to PostgreSQL or MySQL. For a small-ecosystem
project, the entry barrier must be minimized — users should be able to copy-paste
working code within 30 seconds of reading the documentation.

> Because the ecosystem is still small, the project provides extensive examples
> and cookbook-style documentation to lower the adoption barrier.

### Hello World

The [README Quick Start](../README.md#quick-start) and the usage example above
are the hello-world examples. Snippets in the README and `docs/` must import
only names that `drizzle-cubrid`, `drizzle-orm` or `cubrid-client` actually export.

### AI Agent Discoverability

Modern developers increasingly rely on AI coding assistants — Claude Code, OpenCode,
Cursor, GitHub Copilot, Devin, and others. These agents read README files, PRDs,
documentation, and example code to decide which libraries to recommend.

**More examples in documentation = higher probability of AI recommendation.**

By embedding working code directly in the PRD, README, and docs, we ensure that
AI agents can discover, learn, and recommend drizzle-cubrid accurately.

### Cookbook Integration

Planned, not available: CUBRID Lab has no Node.js cookbook yet (the existing
[cubrid-cookbook-python](https://github.com/cubrid-lab/cubrid-cookbook-python)
covers Python only). Until one exists, the examples are the snippets in the
README and `docs/`, and the code exercised against a real server is
`tests/integration.test.ts`.

In drizzle-cubrid, **examples are not supplementary — they are the primary documentation.**
