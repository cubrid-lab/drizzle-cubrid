## [Unreleased]

### Added
- `drizzle-cubrid/native` gets streaming and prepared relational queries (#165, [ADR 0008](docs/adr/0008-prepared-queries-and-streaming.md)). `iterator(placeholderValues?, { literal?, signal?, fetchSize?, consumerTimeout? })` on selects, set operations and prepared selects reads the rows through cubrid-client's `stream()` with `rowMode: 'array'`, decoded by the same codecs as `execute()`: nothing is sent before the first read, one server reply is held at a time, and `break`, a throw, `return()` or an abort closes the cursor and releases the pool connection. cubrid-client 1.4's `stream()` sends values only as literals, and CUBRID matches some values differently as literals than as typed binds (a NULL inside `OR` under `NOT`, trailing spaces in `LIKE`, denormal doubles), so a stream never silently differs from `execute()`: under `binding: 'literal'` both send literals and return the same rows (verified over a 90+ condition matrix); under the default `binding: 'prepared'`, `iterator()` is refused before anything is sent unless the call passes `{ literal: true }` to accept literal semantics (the differences are documented and pinned by live tests), until cubrid-client can stream with typed binds (cubrid-lab/cubrid-client#307). `iterator()` is also refused before anything is sent inside `db.transaction()` (cubrid-client's transaction client has no `stream()`), for a prepared select whose transaction ended, on a client without `stream()`, with unknown or invalid options or an array value, and on relational queries. Relational `findMany()`/`findFirst()` now have `prepare()`: the query is checked and planned once and each `execute(placeholderValues)` runs its statements as an awaited query does; `limit` and `offset` may be `sql.placeholder()`s (refused before, #236), and a placeholder without a value at any level is refused before the root statement is sent. `prepare()` everywhere is documented as a client-side plan, not a server-side prepared statement (cubrid-client prepares and closes a server statement per call); placeholder values that are not an object are refused. `$defaultFn()`/`$onUpdateFn()` values of a prepared write are generated once per `prepare()`, as in Drizzle's own dialects (documented with a warning). Verified live on CUBRID 11.4: 10,000 streamed rows on one pool connection, pool release on early exit and abort, concurrent streams, `stream-busy` on a `CubridClient`, prepared reuse under both bindings, prepared DML and prepared relational queries.
- Experimental CUBRID-native schema migrations for `drizzle-cubrid/native` (#163, [ADR 0009](docs/adr/0009-cubrid-native-migrations.md), [docs/MIGRATIONS.md](docs/MIGRATIONS.md)). A new entry, `drizzle-cubrid/native/migrator`, exports `migrate(db, { migrationsFolder, migrationsTable?, dryRun? })`, `readMigrationFiles(folder)` and `CubridMigrationError`. Migrations are `<number>_<name>.sql` files of CUBRID statements separated by `;`, numbered 1, 2, 3, … without gaps. Before running anything, `migrate()` checks file names, numbering, the SQL of every file and the record table (`__drizzle_cubrid_migrations`: id, name, SHA-256 checksum, UTC `applied_at`), and refuses an edited, renamed or missing applied migration; a database ahead of the folder (records beyond its last file, as during a rolling deploy of an older version) is accepted, nothing is applied and those records are returned as `ahead`; symbolic links in the folder are followed, a folder with no migration is refused, and a leading UTF-8 BOM is ignored. Then it applies each pending migration in its own `'read committed'` transaction together with its record, behind a lock row (`<table>_lock`) so concurrent calls apply each migration once. A failed statement rolls the whole migration back and rejects with `code: 'statement-failed'`, the migration, the statement and the driver error. SQL written for MySQL or generated by drizzle-kit is refused, never rewritten: backtick identifiers, `--> statement-breakpoint`, drizzle-kit `meta/_journal.json` folders, `ENGINE=`, `UNSIGNED`, `ZEROFILL`, `DEFAULT CHARSET`, `/*! */` and `#` comments, `USE`/`DELIMITER`/`LOCK`/`UNLOCK`, transaction control (including `XA`), `SET SYSTEM PARAMETERS`, stored routine bodies, `?` parameters and down migrations. `generateInitialMigration(schema)` in `drizzle-cubrid/native` writes the first migration (`CREATE TABLE` for each native table). Schema diffing, `ALTER` generation, catalog reflection, `push`/`pull` and drizzle-kit in any dialect are not provided. Measured on CUBRID 11.4.7 and kept as live tests: DDL in a cubrid-client `transaction()` rolls back (CREATE/ALTER ADD and DROP COLUMN/CREATE and DROP INDEX/ADD CONSTRAINT/CREATE VIEW/CREATE SERIAL/DROP TABLE/RENAME TABLE), does not commit the DML before it, is invisible to other sessions until commit, and makes their reads of an altered table wait; a failed statement leaves the transaction open; outside `transaction()` the driver autocommits each statement. The live suite applies, reruns, fails and recovers, refuses drift and foreign SQL, accepts a database ahead of an older folder, ignores another owner's table of the record table's name, runs two concurrent `migrate()` calls and round-trips rows through the native query API on the migrated tables; the packed-package checks cover the new entry (ESM, CJS, Node 18). The example in `examples/migration` now uses the native migrator.
- Fault-injection tests on real CUBRID 11.4 (#164): `tests/faults.test.ts` (`npm run integration:faults`, its own `vitest.faults.config.ts`, excluded from `npm test` and the live suite) cuts, stalls and refuses connections through an in-test TCP proxy (`tests/support/fault-proxy.ts`, which can also cut a connection at a chosen CAS request such as COMMIT, before the server sees it or after it answered) and restarts the database server and broker, kills CAS processes and pauses the container through Docker (`CUBRID_TEST_CONTAINER`). 22 tests cover a connection lost in a transaction, restarts between queries, a lost COMMIT (not committed, and committed with the reply lost, both `outcomeUnknown: true` and passed through unchanged), an autocommit write whose COMMIT reply was lost (committed once, never resent), lock timeouts and deadlocks in transactions and savepoints, `readTimeout` on a stall, a paused server and a long lock wait, and a relational query with `with` losing its connection between statements; each asserts the persisted rows through a new connection and that the pool recovers. A new CI job (`fault-cubrid`, part of the CI gate) runs them on their own `docker run` container with the pinned 11.4 image and requires every test to run and pass. [Failures](docs/NATIVE_API.md#failures) documents what callers see per scenario, including the unknown outcome of a failed COMMIT.
- Release gate for real CUBRID (#164): `publish.yml` builds and packs the tarball once, runs the live suite (`tests/integration.test.ts`, every `../src` entry import pointed at the installed package) and a CommonJS smoke test of both entry points against that tarball in a clean consumer on CUBRID 11.4 (pinned digest, `TZ=Asia/Seoul`), with the lockfile peers and with the `drizzle-orm` and `cubrid-client` floors read from `peerDependencies`, requires a non-zero test count with none failed or skipped, records the server version, image digest, Node/peer/package versions, Git SHA, tarball integrity and test counts in the job summary and an evidence artifact, and then publishes that same file (`npm publish <tarball>`) after checking its integrity and that its version matches the tag. Lint, the dialect boundary and the Node 18 packed consumer are part of the gate; unit tests run on Node 20 and 22 (Vitest does not run on Node 18). CI runs the same packed live lanes on every code change (`scripts/packed-live.mjs`). See [what is verified](docs/COMPATIBILITY.md#what-is-verified-and-what-is-not).
- `drizzle-cubrid/native` gets relational queries: `drizzle(client, { schema })` adds `db.query.<table>.findMany()`/`findFirst()` on Drizzle's `relations()` with `columns` (include/exclude), `with` to any depth (one-to-many, many-to-one with nullable keys as `null`, one-to-one in either direction, self relations with `relationName`, many-to-many through a junction table, composite keys), `where`/`orderBy` as values or callbacks, `limit` (per parent when nested) and root `offset`, `extras` at every level, and `tx.query` inside `db.transaction()`; result types are Drizzle's neutral `BuildQueryResult`. CUBRID has no LATERAL and its JSON aggregation loses types, so each relation level is one SELECT with the parents' keys in chunked `IN (...)` lists (a row-value `IN` for composite keys) through the native compiler, stitched in JavaScript: 1 + relations × key chunks statements, never one per parent, and every value is decoded by its column codec (BIGINT, dates, collections). Key columns of another length, precision or scale in the same family (exact numbers, CHAR, VARCHAR) are matched on the reference cast to the parent type; other key type pairs (CHAR with VARCHAR, FLOAT with DOUBLE, …) are refused. A nested `limit` applies per parent with `row_number() over (partition by …)`. Outside a transaction a query with `with` runs as the new `relationalReads` option says: `'snapshot'` (default, a `'repeatable read'` transaction: one snapshot on one connection; a pool not created at `'repeatable read'` closes that connection afterwards), `'client'` (a transaction at the client's own level) or `'separate'`; inside `db.transaction()` it uses the transaction's connection and level. A failed statement keeps the `QueryError` class it has without `with`. Root `offset` without `limit`, nested `offset`, `where`/`orderBy`/`limit`/`offset` on a one relation, and clients without the needed `transaction()` are refused before sending anything. Verified live on CUBRID 11.4 (#158).
- `drizzle-cubrid/native` gets set operations: `union`, `unionAll`, `intersect`, `intersectAll`, `except` and `exceptAll` as select methods, standalone functions and callbacks, as in Drizzle. Operands are parenthesised, so each keeps its own `orderBy()`/`limit()`; chained operators run left to right (`((a) union (b)) intersect (c)`, as CUBRID 11.4 evaluates them); `orderBy()`/`limit()`/`offset()` on the result take fields of the first select, sent as positions. Rows are read by position with the first select's codecs, so an operand field of another SQL type (DATE with DATETIME, which a DATE codec would truncate) is refused, as are operands with other keys, FOR UPDATE in a set operation (-493/-494 on the server) and ordering by anything but a bare or `asc()`/`desc()` field of the first select. A select made into a one-field subquery with `.as()` can be selected as a field (`(select …)`, decoded by that field's codec, and written the same way when used in `where`/`having`/`orderBy`/`groupBy`), including correlated subqueries; a multi-field one (-493 on the server), and one reading a table the outer query reads (which would compare inner rows with themselves), are refused. Tables made with Drizzle's `aliasedTable()` are written as `"table" "alias"` in `from()` and joins; they were written as the alias alone, which CUBRID rejected. Subqueries in `exists()`, `inArray()` and `sql` comparisons are covered by tests. Verified live on CUBRID 11.4 (#158).
- `drizzle-cubrid/native` gets `db.transaction(async (tx) => …, { isolationLevel? })` on cubrid-client's `transaction()`, so every statement of `tx` runs on the transaction's own connection and statements of `db` stay outside it. Nested `tx.transaction()` uses `savepoint "spN"` and `rollback to savepoint "spN"` (CUBRID has no RELEASE); `tx.rollback()` throws `CubridTransactionRollbackError`, a Drizzle `TransactionRollbackError`. The callback's own error is rethrown with cubrid-client's error as `transactionError` and a failed rollback as `rollbackError`; a failed commit is cubrid-client's error, unchanged. `'read committed'`, `'repeatable read'` and `'serializable'` are passed to the driver; other levels, `accessMode`, `withConsistentSnapshot`, other keys, clients without `transaction()` and concurrent nested transactions of one level are refused before anything is sent. A `tx` used after its callback settled throws before sending anything. While a nested transaction runs, statements of the enclosing level are refused (its rollback would undo them); a nested transaction still running when a callback returns, or a failed rollback to a savepoint, makes that level roll back instead of committing. Verified live on CUBRID 11.4 (#161).
- `drizzle-cubrid/native` gets `insert()`, `update()` and `delete()`: `values(row | rows)` with missing columns written as `DEFAULT` and `$defaultFn()`/`$onUpdateFn()` values generated per row, `select()` for INSERT … SELECT from a native select, `onDuplicateKeyUpdate({ set })`, update `where`/`orderBy`/`limit`, delete `where`/`limit`, `prepare()` and `toSQL()`. They resolve to `CubridDmlResult` (`affectedRows`, `lastInsertId`) from cubrid-client's `executePrepared()` (`execute()` under `binding: 'literal'`), unchanged, with a `bigint` id kept exact. `$returningId()` returns one-row AUTO_INCREMENT keys from the keys the server says the INSERT generated (cubrid-client `generatedKeys: true`; CUBRID 11.0–11.4 rejects that on a table with an INSERT trigger, -983, before inserting), throwing if an inserted row's key is still unreported and `$defaultFn()` keys normalised through the column codec; with `onDuplicateKeyUpdate()` it reports keys only of an inserted row. It refuses a multi-row INSERT with an AUTO_INCREMENT key, a multi-row upsert and INSERT … SELECT before sending. SET, MULTISET and SEQUENCE values are written as typed `CAST(SET{?, …} AS SET(T))` literals, including empty ones. Empty `values()`/`set()`, DELETE with ORDER BY, INSERT IGNORE and RETURNING are refused or not provided; `values(col)` in `onDuplicateKeyUpdate()` is not supported (#159).
- `drizzle-cubrid/native` gets `drizzle(client)` with a native SELECT builder and session: `select()`/`selectDistinct()` with inner, left, right and cross joins, `where`, `groupBy`, `having`, `orderBy`, `limit`/`offset`, `.for('update')`, subqueries with `.as()`, `prepare()` with placeholders, `toSQL()` and `db.execute()`. Rows are read with `rowMode: 'array'` and mapped by position; values are typed binds by default (`binding: 'literal'` opts out); identifiers are double-quoted with embedded quotes doubled; date and time reads are refused from a client that does not decode in UTC. FULL JOIN, lateral joins, `offset()` without `limit()`, `for('share')`/`noWait`/`skipLocked` and collection values in conditions are refused (#158, #160).
- Experimental `drizzle-cubrid/native` entry point, the first slice of the CUBRID-native dialect (ADR 0007): `cubridTable()` with composite `primaryKey()` and `unique()` constraints, and column builders with CUBRID SQL types and codecs: `smallint`, `integer`/`int`, `bigint` (`mode: 'bigint'` exact; `mode: 'number'` throws beyond 2^53 − 1 instead of rounding), `numeric`/`decimal` (exact strings by default), `float`, `double`, `char`, `varchar`, `string`, `boolean` (SMALLINT 0/1), `datetime`, `timestamp`, `date`, `time` (UTC wall clock), `monetary`, and `set`/`multiset`/`sequence` with per-element codecs. It has no query builder or session yet and is not for production; see [docs/NATIVE_API.md](docs/NATIVE_API.md). The root `drizzle-cubrid` entry is unchanged (#157, #162).
- Lint and formatting are enforced in CI with Biome, pinned to 2.6.7: `npm run lint` runs `biome ci --error-on-warnings .` and `npm run format` applies fixes. The unused ESLint scripts and dependencies, which had no configuration and could not run, are removed (#167).
- Live CUBRID tests (`tests/integration.test.ts`, `npm run integration`) for transactions, joins, write metadata and collections, run in CI against CUBRID 11.4 (#181, #164).

### Fixed
- `inArray()` and `notInArray()` with two or more `sql.placeholder()` values on a CHAR column, in a prepared query under the default typed binding, matched no row (`IN`) or every non-NULL row (`NOT IN`), in both `drizzle-cubrid` and `drizzle-cubrid/native`: a placeholder has no column, so #237's `cast(? as CHAR(n))` did not reach it. Under typed binds, such a list (exactly as `inArray()`/`notInArray()` build it, two or more elements, one a placeholder, on a `char()` column) is now sent as `(c = ? or c = ?)` / `(c <> ? and c <> ?)`, in `where` and in selected fields (the 0.x single-table selection included); each `= ?` compares padded. On CUBRID 11.4 that gave the same rows and true/false/NULL values as `IN`/`NOT IN` in every case tested, NULL placeholder values and `not()` of the list included, and a value longer than the column matches nothing (a `cast(? as CHAR(n))` would fail with -494 under typed binds and truncate into a match with literals). Under `binding: 'literal'` the SQL is unchanged: literal lists were never affected, and with literals CUBRID takes `code = NULL` inside `OR` as false, so the expanded form would differ under `not()`. `eq()` with a placeholder, one-element lists, lists of values only, VARCHAR columns and other `sql` templates are sent as before. The 0.x dialect now throws a clear "unsupported drizzle-orm version" error if `MySqlDialect` has no casing cache. The docs now say that a CHAR column compares unpadded with any VARCHAR expression or subquery and to cast those to CHAR. Verified live on CUBRID 11.4 (#239).
- `inArray()` and `notInArray()` with two or more values on a CHAR column matched no row (`IN`) or every non-NULL row (`NOT IN`) under the default typed binding, in both `drizzle-cubrid` and `drizzle-cubrid/native`: CUBRID 11.4 types the bound values of such an `IN` list as `VARCHAR` and compares a `CHAR` column with `VARCHAR` values without space padding, whichever bind type the driver sends (and also in plain SQL, `code in (cast('ab' as varchar), …)`). A string bound to a `char()` column is now sent as `cast(? as CHAR(n))`, in comparisons and writes, under both bindings; a value longer than `n` is cast to its own UTF-8 byte length so it never matches by truncation. Writes store the same values as before. `sql.placeholder()` values are not cast (lists of them are handled by #239's fix); native relational queries no longer cast CHAR keys themselves. Verified live on CUBRID 11.4 (#237).
- `package.json` `exports` give `require` consumers the `.d.cts` declarations (nested `import`/`require` conditions); TypeScript with `moduleResolution: node16` resolved the ESM `.d.ts` for CommonJS before.
- `monetary()` columns returned the driver's number although typed as `string`; they now return the number's shortest decimal string (`12.34` → `'12.34'`). Code that did arithmetic on the value without converting it now gets a string (#217).
- `datetime`, `timestamp`, `date` and `time` columns read cubrid-client's `Date` values. `select()` of a `datetime()` or `timestamp()` column threw `value.replace is not a function`, `date()` came back shifted by the process's UTC offset, and `mode: 'string'` columns returned a `Date` (#207).
- `db.$count(table, where?)` failed with `SqlSyntaxError`: Drizzle aliases the count `as count`, a reserved word in CUBRID, and read a mysql2-shaped result. The alias is dropped and the count read by position; it works in transactions and as a subquery (#199).
- Statement values are sent as typed binds through cubrid-client's `queryPrepared()`/`executePrepared()` instead of being written into the SQL text, despite the prepared-query naming (#191).
- Collection values are written as `CAST(SET{?, ?} AS SET(<element type>))`: with typed binds CUBRID refused `UPDATE ... SET q = SEQUENCE{?, ?}` (-494, cannot coerce host var). String elements, and collections without `element`, cast to `STRING`, except CHAR elements, which cast to their `CHAR(n)` so `eq()` on a CHAR collection still matches; element types with no known SQL type are not cast.
- Collection DDL now maps `bigint`, `double`, `float`, `boolean`, `datetime`, `timestamp`, `date` and `time` elements to their CUBRID types instead of `NUMBER`, `DATE` or the Drizzle JavaScript category.
- `insert`, `update` and `delete` report `affectedRows` and `lastInsertId` from cubrid-client's `execute()`; they returned `[]` with no counts. `$returningId()` returned `[]` and now returns the key of a one-row INSERT, keeping a `bigint` key exact (#182).
- SET, MULTISET and SEQUENCE columns: values are written as typed collection literals with one parameter per element (`SET{?, ?}`) and read as the arrays cubrid-client returns. Writing failed (`item.replaceAll is not a function`, or a SQL error) and reading parsed arrays as text (#184).
- Selected fields are now read from `query(sql, params, { rowMode: 'array' })` in select-list order instead of `Object.values()` of object rows. Joins whose tables share column names (`id`, `name`) returned one table's values under the other's fields; a partial select could return the wrong column under a field name (#183).
- `db.transaction()` now runs on a connection owned by `cubrid-client`'s `transaction()` instead of `BEGIN`/`COMMIT` on the shared client, so concurrent queries can no longer join, commit or roll back another request's transaction (#185).
- A failed `ROLLBACK TO SAVEPOINT` no longer replaces the nested callback's error; it is attached as `rollbackError`.

### Changed
- The foreign-dialect boundary guard (`npm run check:boundary`, #192) gets a `native-dynamic` rule for `src/native/**` and the packed native entries (`dist/native*.{js,cjs,mjs}`): `eval`, `Function`, `.constructor(...)` calls, non-literal `import()`/`require()` and `'require'`/`'createRequire'`/`'eval'`/`'Function'` as computed keys can no longer load foreign dialect code unseen by the specifier checks. It cannot be baselined; the 0.x baseline (176 `src`, 343 packed findings) is unchanged.
- Codecov is removed (#172): `codecov.yml` and the README coverage badge are deleted, since nothing uploaded coverage to it. The enforced coverage gate is unchanged: the 95% Vitest thresholds in `vitest.config.ts`, run by `npm test` and CI.
- Docs: [NATIVE_API.md](docs/NATIVE_API.md#not-supported-in-the-native-dialect) lists the CUBRID types that `drizzle-cubrid/native` has no builder for (zone-aware temporal types, `BLOB`, `CLOB`, `ENUM`, `JSON`), what to do instead, and that they are not planned for 1.0; `BIT`/`BINARY` are tracked in #216 (#162).
- SQL that Drizzle's MySQL builders emit and CUBRID 11.4 always rejects with a generic -493 syntax error is refused before it is sent, with an error naming the alternative: `ilike()`/`notIlike()`, `.offset()` without `.limit()`, lateral joins, `.for('share')` and the `noWait`/`skipLocked` options, `insert().ignore()` and `delete().orderBy()`. CUBRID rejected each of these on the server. The refusal is thrown while the query is built, so `.catch()` on such a query throws synchronously; raw SQL given to `db.execute()` is refused if it uses ILIKE outside quotes and comments (#189).
- Relational queries that load relations with `with` now throw `Relational queries with 'with' (...) are not supported on CUBRID` before sending anything. In `mode: "default"` they failed with a syntax error (CUBRID has no `LEFT JOIN LATERAL`); in `mode: "planetscale"` CUBRID's JSON aggregation rejected DATE/DATETIME columns and garbled non-ASCII text in ISO-8859-1 databases, and Drizzle's `JSON.parse` of it rounded BIGINT values beyond 2^53. **Breaking for planetscale mode:** `with` on relations whose columns are only integers and ASCII (or any text in a UTF-8 database) returned correct results before and now throws. `findMany()`/`findFirst()` without `with` are unchanged (#200).
- **Breaking:** date and time columns follow Drizzle's MySQL convention, where the stored wall clock is UTC, and are read only from a client that decodes in UTC: create it with `timezone: 'utc'` or run with `TZ=UTC`. Selecting them with `select()` or `db.query` through a local-zone client in a non-UTC process is refused before the query is sent; other columns and `extras` that return a `Date` are passed through as they are (#207, #210).
- CUBRID's TIMESTAMP and TIME hold whole seconds and drop fractional seconds without an error; this is documented in `docs/SCHEMA.md`, and comparisons such as `gt(t.ts, new Date())` keep working (#207).
- **Breaking:** `date()` returns midnight UTC of the stored date; `mode: 'string'` columns return strings: `datetime` `YYYY-MM-DD HH:MM:SS.mmm`, `timestamp` `YYYY-MM-DD HH:MM:SS`, `date` `YYYY-MM-DD`, and `time` `HH:MM:SS` (#207).
- New `binding` option for `drizzle()`: `'prepared'` (default) or `'literal'`. Under the default, `drizzle()` throws at construction for a custom client without `queryPrepared()`, or with `execute()` but no `executePrepared()`, instead of falling back to SQL literals or losing write counts.
- `$returningId()` with an AUTO_INCREMENT key refuses a multi-row INSERT before sending it, since CUBRID does not report or promise consecutive keys. The result of `insert`, `update` and `delete` is typed `CubridRawQueryResult` with optional `affectedRows` and `lastInsertId`.
- Collection builders take a type parameter for the element type (`cubridSet<number>(...)`, `string` by default) and refuse non-array values and unsupported elements; the old brace-string parser and writer are removed.
- A custom client passed to `drizzle()` must return array rows from `query(sql, params, { rowMode: 'array' })`; object rows are refused for selects that map fields.
- Peer ranges are now `drizzle-orm >=0.44.1 <0.46.0` and `cubrid-client >=1.4.0 <2.0.0`. Older `drizzle-orm` versions fail to type-check (`tsc --noEmit`); see `docs/COMPATIBILITY.md` (#186).
- `accessMode`, `withConsistentSnapshot` and `isolationLevel: "read uncommitted"` are rejected, since CUBRID does not support them. `isolationLevel` needs cubrid-client 1.3.0 or later and is rejected with older drivers instead of being ignored.
- A custom client passed to `drizzle()` that has a `transaction` method must accept `(callback, options?)` and run the callback on the transaction's connection; `db.transaction()` now calls it.
- A callback error is rethrown as the same object with the driver's error attached as `transactionError` (and `rollbackError` when rolling back failed).

## [0.1.0] - 2026-03-13

### Added
- Initial release
- Drizzle ORM dialect for CUBRID database built on `mysql-core`
- `drizzle()` factory function with full type inference
- `cubridTable` — table builder (alias for `mysqlTable`)
- All MySQL-compatible column types (except JSON, which CUBRID does not support)
- CUBRID-specific custom types: `SET`, `MULTISET`, `SEQUENCE`, `MONETARY`
- `CubridSession`, `CubridPreparedQuery`, `CubridTransaction` — session layer
- Transaction support with savepoints (without `RELEASE SAVEPOINT`)
- Full query builder support: SELECT, INSERT, UPDATE, DELETE, JOIN
- Dual module format: ESM + CJS with TypeScript declarations
- 49 offline tests with 99%+ code coverage
